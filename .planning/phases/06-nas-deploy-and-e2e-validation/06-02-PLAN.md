**Step 5 — Verify Sonarr hardlinks with inode check:**

After the proxy logs show hardlinks were created:
```bash
# List hardlinks in library path (adjust Series/Season based on actual grab)
ssh root@192.168.10.199 "docker exec prowlarr-llm-proxy ls -li /data/media/tv/"
# Then drill into the specific series/season directory
ssh root@192.168.10.199 "docker exec prowlarr-llm-proxy ls -li '/data/media/tv/{Series}/Season {NN}/'"
```

**Verification criteria:**
- Files exist at the correct path structure: `{SONARR_LIBRARY_PATH}/{Series}/Season {NN}/{file}`
- `ls -li` output shows link count >= 2 (second column after inode number)
- The inode number matches the original file in the download directory

Verify original files are untouched:
```bash
# Find the torrent download folder and check inodes match
ssh root@192.168.10.199 "docker exec prowlarr-llm-proxy ls -li /data/torrents/{torrent-folder}/"
```

Same inode number + link count >= 2 confirms hardlink (not copy). This is BLOCKING -- if link count is 1 or inodes differ, the hardlink pipeline is broken.

**Troubleshooting if hardlinks don't appear:**

1. Check logs: `ssh root@192.168.10.199 "docker logs prowlarr-llm-proxy --tail 100 | grep -i 'grab\|hardlink\|error\|warning'"`
2. Did webhook arrive? Look for "Received Sonarr Grab webhook" in logs
3. Did metadata resolve? Look for qBittorrent polling logs
4. Cross-device error? Look for "CrossDeviceError" or "different devices"
5. HardlinkService None? Look for "HardlinkService not available" -- means USE_NEW_HANDLER factory failed
6. Path mismatch? Compare DOWNLOAD_PATH in .env vs actual torrent download location
